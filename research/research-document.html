1 User Secrets

Source: Safe storage of app secrets in development — learn.microsoft.com/.../security/app-secrets

What are User Secrets in ASP.NET Core?

A development-time tool (the dotnet user-secrets CLI, backed by Microsoft.Extensions.Configuration.UserSecrets) that stores sensitive configuration values — such as API keys or connection strings — in a JSON file that lives outside the project folder, on the developer's own machine, instead of inside the source code.

What problem do User Secrets solve?

Without them, developers tend to put real credentials directly in appsettings.json. Since that file is part of the repository, the credentials get committed to source control and stay in the git history even after being deleted later. User Secrets remove this risk by keeping the values physically separate from the project tree.

Where are User Secrets stored?

OSLocation
Windows%APPDATA%\Microsoft\UserSecrets\<id>\secrets.json
Linux~/.microsoft/usersecrets/<id>/secrets.json
macOS~/.microsoft/usersecrets/<id>/secrets.json

Are User Secrets encrypted? Trusted production store?

No — stored as plain, unencrypted JSON. Safety comes only from being outside the project directory. Not considered a trusted production secret store; production secrets should use a managed vault (e.g. Azure Key Vault) instead.

How is a project connected to its store? (UserSecretsId)

Running dotnet user-secrets init adds a <UserSecretsId> GUID to the .csproj:

<PropertyGroup>
  <UserSecretsId>a1b2c3d4-example-guid</UserSecretsId>
</PropertyGroup>

The GUID maps the project to its own secrets folder on disk, so each project on a machine keeps isolated secrets.

Commands: init, set, list, remove, clear

dotnet user-secrets init
dotnet user-secrets set "Key" "Value"
dotnet user-secrets list
dotnet user-secrets remove "Key"
dotnet user-secrets clear

Original example used in the implementation:

dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Server=localhost;Database=ProductDb;Trusted_Connection=True;"

How does the app read a secret through IConfiguration?

For Web SDK projects, the User Secrets provider is added automatically in Development. No extra setup is needed:

var connectionString = builder.Configuration["ConnectionStrings:DefaultConnection"];

When should User Secrets be used / not be used?

UseDon't use
Local database credentials on a dev machineAnything deployed with the app
API keys for local testingProduction credentials
Any short-lived local-only valueSecrets shared across a team

Why must User Secrets not contain production credentials?

They are unencrypted, live only on one developer's machine (so they don't travel with deployment), and have no access-control mechanism. A compromised machine would expose them in plain text with no extra protection layer.

2 Environment Variables

Sources: Configuration in ASP.NET Core · Use multiple environments

What is an environment variable?

A key-value pair stored at the OS/process level, outside any application file, readable by a running process at startup or runtime.

Who can create them?

The OS itself, the terminal session, the IDE (launch profiles), a container/orchestrator (Docker, Kubernetes), or a cloud host (Azure App Service "Application Settings" are exposed as environment variables).

How does ASP.NET Core load them into IConfiguration?

The default host builder adds the Environment Variables configuration provider automatically; every visible environment variable becomes a configuration key-value pair.

Hierarchical keys — the double underscore separator

Colons (:) nest keys in IConfiguration, but colons are not valid in environment variable names on every shell (Bash in particular). ASP.NET Core uses __ instead, converting it to : automatically when read.

// Env var:  Logging__LogLevel__Default=Warning
var level = builder.Configuration["Logging:LogLevel:Default"]; // "Warning"

Setting them temporarily per tool

# PowerShell
$env:ASPNETCORE_ENVIRONMENT = "Development"

:: Command Prompt
set ASPNETCORE_ENVIRONMENT=Development

# Bash
export ASPNETCORE_ENVIRONMENT=Development
  • Visual Studio: Launch Profiles / launchSettings.json (dev only, not published)
  • Docker: docker run -e ASPNETCORE_ENVIRONMENT=Production ...
  • Azure App Service: "Application Settings" in the portal

What is ASPNETCORE_ENVIRONMENT?

The variable ASP.NET Core reads to set IWebHostEnvironment.EnvironmentName. Conventional values: Development, Staging, Production. Defaults to Production if unset.

Environment name vs. environment variable

ASPNETCORE_ENVIRONMENT is an environment variable, but "environment name" is the broader concept it controls. Other environment variables exist that have nothing to do with the environment name.

Do environment variables automatically encrypt secrets?

No, they are plain unencrypted text at the OS/process level.

When are they more suitable than User Secrets?

When a value must reach a deployed environment — User Secrets never leave the dev machine, while environment variables are the standard deploy-time injection mechanism across hosting platforms.

Risks of sensitive values in environment variables

If the host/container/process is compromised, environment variables can be read by anyone with process access (e.g. /proc/<pid>/environ on Linux). They can also leak via logs, crash dumps, or child-process inheritance. Managed vaults with access control and encryption at rest are safer for real production secrets.

3 appsettings Files & Configuration Sources

Source: Configuration in ASP.NET Core — learn.microsoft.com/.../fundamentals/configuration

What is appsettings.json, and when is it loaded?

The default JSON configuration file for an ASP.NET Core app. It is loaded early in the host-building process, before the app starts handling requests, and is added as the base configuration provider regardless of environment.

appsettings.{Environment}.json

An environment-specific overlay file loaded after the base appsettings.json, so its values override the base file's for matching keys. Examples: appsettings.Development.json, appsettings.Staging.json, appsettings.Production.json. Only the file matching the current ASPNETCORE_ENVIRONMENT is loaded, on top of the base file.

Default configuration precedence

Providers are added in order, and later providers override earlier ones for the same key. The default order (roughly):

  1. appsettings.json
  2. appsettings.{Environment}.json
  3. User Secrets (Development only)
  4. Environment variables
  5. Command-line arguments

Which provider wins if the same key exists everywhere?

The command-line argument wins, because it's added last in the default pipeline. Between the others named in the question, an environment variable overrides a User Secret, which overrides appsettings.json.

What belongs safely in appsettings.json?

Non-sensitive, stable settings: logging levels, feature flags, non-credentialed URLs, timeouts, pagination sizes, and similar application behavior settings.

What must never be committed to appsettings.json?

Passwords, API keys, credentialed connection strings, certificate passwords, or any value that grants access to a real system.

Is a connection string always a secret?

Not necessarily. A credentialed connection string (contains a username/password, e.g. SQL Authentication) is a secret and must never be committed. A non-credentialed connection string (e.g. using Trusted_Connection=True / Windows/Integrated Authentication, with no embedded password) carries less risk, though the server/database name itself can still be considered sensitive depending on context.

User Secrets vs. environment variables/managed store — when each

A developer working locally should use User Secrets for their own machine-only credentials. A deployment (staging/production) should use environment variables or a managed secret store, since User Secrets are not deployed with the app and are not designed for shared or production use.

IConfiguration vs. the Options pattern

IConfiguration is a low-level, string-key/dictionary-style API for reading raw configuration values anywhere in the app. The Options pattern (IOptions<T>, IOptionsSnapshot<T>) binds a section of configuration to a strongly-typed class, injected via DI. IConfiguration is appropriate for quick, one-off reads (like a connection string at startup); the Options pattern is appropriate for larger, structured settings that a service depends on repeatedly, since it gives compile-time safety and testability.

4 Kestrel Configuration

Sources: Kestrel web server in ASP.NET Core · Configure endpoints for Kestrel

What is Kestrel, and what role does it play?

Kestrel is the cross-platform web server built into ASP.NET Core. It is the component that actually accepts TCP connections and turns raw bytes into HTTP requests the middleware pipeline can process. It ships with every ASP.NET Core project template by default.

What is a Kestrel endpoint?

The combination of an address (the network interface/port Kestrel listens on) and a protocol (HTTP/1.1, HTTP/2, HTTP/3, optionally secured with TLS/HTTPS).

What properties can be configured per endpoint?

Address (host/IP), port, protocol/scheme (http/https), and certificate (for HTTPS endpoints).

Ways to configure Kestrel endpoints

  • appsettings.json — a Kestrel:Endpoints JSON section
  • Environment variables — e.g. ASPNETCORE_URLS
  • Command line — --urls argument
  • C# code — KestrelServerOptions via webBuilder.ConfigureKestrel(...) or options.Listen(...)

Configuration used in the implementation:

"Kestrel": {
  "Endpoints": {
    "Http":  { "Url": "http://localhost:5097" },
    "Https": { "Url": "https://localhost:7097" }
  }
}

Why configure Kestrel in appsettings.json?

It keeps endpoint configuration declarative, easy to read, and reloadable without recompiling, and it can be overridden per environment file just like any other setting.

When is appsettings.json not the best place for final production endpoints?

When the actual binding needs to be decided by the hosting environment itself at deploy time (a container orchestrator assigning a port, or a cloud host injecting PORT/ASPNETCORE_URLS dynamically) — in that case an environment variable is more appropriate than a hardcoded file value.

localhost vs. 0.0.0.0 vs. a specific IP

ValueMeaning
localhostOnly accepts connections from the same machine (loopback)
0.0.0.0Wildcard — binds to all available network interfaces (accessible from other machines on the network)
Specific IPBinds only to that one network interface

Configuring separate HTTP and HTTPS endpoints

Define two named entries under Kestrel:Endpoints in appsettings (or two Listen calls in code) — one with an http:// URL and one with an https:// URL, each on its own port, as shown above.

HTTPS endpoint with no explicit certificate in Development?

Kestrel automatically falls back to the local ASP.NET Core HTTPS development certificate (created and trusted via dotnet dev-certs https --trust). This certificate is not installed in non-development environments.

Where should the certificate path/password be stored?

The certificate path can live in configuration (appsettings or environment variable) since it's not sensitive by itself. The certificate password must be treated as a secret — User Secrets in development, environment variables or a managed vault in production — never committed to appsettings.json.

Kestrel hosting with IIS / Nginx / a load balancer / an ingress

In these setups the reverse proxy sits in front of Kestrel and can terminate TLS itself, forwarding plain HTTP to Kestrel internally (or forwarding HTTPS through, depending on configuration). Kestrel can still run standalone and be exposed directly to the internet, but production apps commonly place a reverse proxy in front for things like load balancing, additional security hardening, and centralized certificate management.

5 Logging, ILogger & Serilog

Sources: Logging in .NET Core and ASP.NET Core · Serilog — Getting Started (official wiki) · Serilog.AspNetCore (official repo) · Serilog.Sinks.File (official repo)

What is application logging and why is it required in production?

Logging is the practice of recording events that happen while an application runs, so that behavior, errors, and performance can be understood after the fact. In production, logs are often the only way to diagnose an issue, since a developer usually cannot attach a debugger to a live system.

.NET log levels, with two realistic situations each

LevelSituation 1Situation 2
TraceLogging every step inside a complex calculation while debugging locallyRecording raw request/response payloads during deep troubleshooting
DebugLogging a computed cache key before a lookupLogging which branch of an if/else a request took
Information"Product created successfully, ProductId: 5"Application startup completed
WarningA requested product ID was not found (expected, recoverable)A retried operation succeeded only on the second attempt
ErrorA database call threw an exceptionA required external API call failed
CriticalThe application cannot connect to its database at startupThe application is about to crash due to an unrecoverable state
NoneSpecial value used to disable logging entirely for a category — not used to log an actual event

What does a configured minimum log level mean?

Only events at or above the configured minimum level are actually recorded; anything below it is discarded before it reaches any provider/sink. For example, a minimum level of Warning means Trace/Debug/Information events are dropped.

What is ILogger?

ILogger (and its generic form ILogger<T>) is the core logging abstraction in Microsoft.Extensions.Logging. ILogger<T> automatically tags every log entry with the category name T (typically the class it's injected into), which makes it easy to filter or search logs by the component that produced them.

How is ILogger obtained through DI?

It's injected via the constructor, exactly like any other service:

public ProductService(AppDbContext context, ILogger<ProductService> logger)
{
    _context = context;
    _logger = logger;
}

What is a logging provider? Console & Debug providers

A logging provider is a plug-in that decides where a log entry actually ends up (console, debug window, file, cloud service, etc.) — ILogger itself is provider-agnostic. The built-in Console provider writes to the terminal/output window, useful during local development. The built-in Debug provider writes to the debugger's output window (e.g. Visual Studio's Debug pane) and only has an effect when a debugger is attached.

Structured logging vs. string interpolation

Structured logging uses a message template with named placeholders:

_logger.LogInformation("Product created successfully. ProductId: {ProductId}", product.Id);

This keeps ProductId as a separate, queryable, typed property in the underlying log event — a structured log sink can filter or search by it directly. String interpolation ($"Product created. Id: {product.Id}") instead bakes the value into a single opaque text string, losing that structure and making later querying/filtering much harder.

What must never be written to logs?

Passwords, connection strings with credentials, full credit card numbers, authentication tokens, and other personally identifiable or secret information.

What is Serilog, and how does it integrate with Microsoft.Extensions.Logging?

Serilog is a third-party structured logging library for .NET. It integrates with the built-in ILogger abstraction through the Serilog.AspNetCore package: once wired up, code that already uses ILogger keeps working unchanged, while Serilog takes over as the actual logging backend, adding richer sinks, enrichers, and structured output formats.

What is a Serilog sink?

A sink is a destination Serilog writes log events to — console, a file, a database, or a log-aggregation service. Multiple sinks can be active at once, each receiving the same stream of events.

Writing Serilog events to console and file

Configured either in code or via an appsettings.json Serilog section read by Serilog.Settings.Configuration:

"Serilog": {
  "WriteTo": [
    { "Name": "Console" },
    { "Name": "File", "Args": { "path": "logs/log-.txt", "rollingInterval": "Day" } }
  ]
}

Daily rolling files, size limits, retained-file limits

The File sink supports rollingInterval: Day to start a new file each day (e.g. log20260915.txt), a file size limit (default 1 GB, configurable) after which no further events are written until the next roll point, and a retained-file-count limit to automatically delete the oldest files once a maximum number of files is reached — keeping disk usage bounded.

Request logging in Serilog.AspNetCore

Calling app.UseSerilogRequestLogging(); in the middleware pipeline adds a single, structured log entry per HTTP request (method, path, status code, elapsed time), replacing the noisier multi-line default ASP.NET Core request logging with one compact structured event per request.

When are local log files unsuitable?

In containers, the filesystem is often ephemeral — logs written to a local file disappear when the container is destroyed or restarted. Across multiple application instances (scaled-out deployments, load-balanced containers), logs end up scattered across many machines with no single place to search them. In both cases, a centralized log sink (a log aggregation service reachable over the network) is more appropriate than writing to local disk.

8 Applying HTTPS theory + implemented

Sources: Enforce HTTPS in ASP.NET Core · Configure endpoints for Kestrel

HTTP vs. HTTPS vs. TLS vs. an HTTPS certificate

  • HTTP — the plain application protocol used to exchange requests/responses; data travels unencrypted.
  • TLS — the protocol that actually performs the encryption/authentication (the modern successor to SSL).
  • HTTPS — simply HTTP running over a TLS-secured connection.
  • HTTPS certificate — the digital file proving the server's identity and carrying the key material TLS uses to encrypt the connection; without it, TLS/HTTPS cannot be established.

dotnet dev-certs commands

dotnet dev-certs https --check           # check if a valid cert exists
dotnet dev-certs https --trust           # create (if needed) and trust it
dotnet dev-certs https --clean           # remove existing dev certificates
dotnet dev-certs https --check --trust   # check + trust in one step

Used in the implementation: dotnet dev-certs https --check --trust reported an existing but untrusted certificate; running dotnet dev-certs https --trust prompted a Windows confirmation dialog and completed with "Successfully trusted the existing HTTPS certificate."

Configuring local HTTP and HTTPS Kestrel endpoints

Both projects define an explicit Kestrel:Endpoints section in appsettings.json with separate Http and Https entries on different ports, so the app listens on both protocols simultaneously (see Part 4 for the exact JSON).

HTTPS redirection middleware — where it belongs

Added early in the pipeline, immediately after var app = builder.Build(); and before any endpoint mapping (app.MapPost, app.UseFastEndpoints(), etc.):

var app = builder.Build();
app.UseHttpsRedirection();
// ... endpoints ...

It must run before anything that could otherwise handle or respond to the plain-HTTP request, so the redirect actually happens before any business logic runs.

Default HTTPS redirection status code

UseHttpsRedirection() uses 307 (Temporary Redirect) by default. 307 is used instead of 301/302 specifically because it preserves the original HTTP method (POST stays POST, DELETE stays DELETE) across the redirect, whereas some clients silently downgrade 301/302 redirects to GET.

Why a production API should listen only on HTTPS rather than rely on a redirect

If the server accepts HTTP at all, there is a brief window where a request (and any data in it) is transmitted unencrypted before the redirect completes. For an API handling sensitive data, it's safer to not expose an HTTP listener at all in production, so no request path ever carries unencrypted traffic.

What is HSTS? Do non-browser clients like Postman enforce it?

HSTS (HTTP Strict Transport Security) is a response header that tells a browser to always use HTTPS for a given host from then on, even if the user types a plain http:// URL, for the duration specified in the header. It is a browser-enforced policy. Non-browser HTTP clients such as Postman do not implement or enforce HSTS — they will still make a plain HTTP request if pointed at an http:// URL and simply follow whatever redirect (or lack of one) the server returns.

Direct TLS termination in Kestrel vs. termination at a reverse proxy

With direct termination, Kestrel itself holds the certificate and decrypts TLS traffic, and the encrypted connection exists all the way to the application process. With reverse-proxy termination (IIS, Nginx, a load balancer, an ingress controller), the proxy holds the certificate and decrypts the incoming HTTPS traffic, then typically forwards plain HTTP to Kestrel over an internal, trusted network. The proxy approach centralizes certificate management and offloads TLS processing, at the cost of the internal hop between proxy and Kestrel being unencrypted (acceptable when that hop stays inside a trusted internal network).

Supplying production certificate paths/passwords without committing secrets

The certificate path can be set via configuration (appsettings or an environment variable), since the path itself isn't sensitive. The certificate password must come from a secret store appropriate to the environment — an environment variable injected by the deployment platform, or a managed secret store/vault — never hardcoded or committed to source control.

Testing over HTTPS with Postman

Both projects were tested successfully against their HTTPS endpoints (e.g. https://localhost:7097/products) after trusting the local development certificate. Requesting the HTTP endpoint (e.g. http://localhost:7097 — the wrong port for the protocol) produced a socket hang up error, which was resolved by matching the correct HTTP port to the plain-HTTP URL and the HTTPS port to the https:// URL.

Solving an untrusted local development certificate

The correct fix is dotnet dev-certs https --trust, which installs the existing local development certificate into the OS's trusted certificate store (prompting a confirmation dialog on Windows). This is the supported, documented approach — rather than disabling certificate validation in the client, which would hide real certificate problems instead of fixing them.
